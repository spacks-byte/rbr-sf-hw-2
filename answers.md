1. The working directory contains the files you are currently editing on a specific device/s. The staging area holds the changes selected for the next commit. A commit is a saved snapshot of those staged changes in local Git history. A remote repository is a copy of the repository hosted elsewhere such as GitHub.
2. 'HEAD' indicates the commit I currently have checked out usually by pointing to the current branch. 'main' is the name of the primary branch in this HW2 repository. 'origin' is the read only reference of the main branch on a remote repository such as GitHub.
3. Other people may have added changes to main since my repo was last updated locally. Fetching or pulling first lets me ensure I am working on the latest code. This reduces the risk of developing against outdated code and makes integration easier decreasing future conflicts.
4. git fetch downloads new commits and updates remote-tracking branches like origin/main without changing my current working branch. git pull fetches those changes and then integrates them into my current branch.
5. Merging combines the histories of two branches often creating a merge commit while preserving their original commit history. Rebasing moves commits onto a different base creating new commit IDs and a more linear history. Rebasing a shared branch is dangerous because it rewrites commits that others may already depend on potentially causing confusing history and difficult synchronization especially if they are working on the branches you rebase.
6. Pull requests provide a place to review code discuss changes and run automated checks before merging into a shared branch. They are helpfult in catching bugs and keeping track of why changes were made.
7. Both main and can had gained separate commits after the branch was created so neither branch was simply ahead of the other and able to be merged into. Git needed a merge commit to join these two lines of history and record that the changes from both branches were combined.
8. Only main changed can_id, so Git could keep that change automatically without choosing between two different edits. Both branches changed the same areas containing @version and loop() in different ways so Git could not safely determine which version to keep.
9. Pushing to ci triggered the PlatformIO CI workflow which builds the project. The Doxygen GitHub Pages Deploy Action did not run because it was configured to run on pushes to main not ci. CI helps protect the team from integrating code that fails to compile or otherwise fails the automated checks.
10. A .gitignore file tells Git which untracked files or folders it should normally ignore. It does not remove files that have already been committed because those files are already tracked they must be explicitly removed from tracking if needed. The .pio folder contains PlatformIO-generated build files dependencies, and other local artifacts that can be recreated so it should not be committed.
